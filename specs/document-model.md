# document-model

Owns: `packages/editor-core/**` (see `specs/ownership.json`). Implemented by `packages/editor-core`
as of milestone M1 (document core: `EditorDocument`, `applyCommand`, `HistoryStack`,
`GraphEdit`/`SceneEdit` command factories, byte-preserving `save`).

`editor-core` holds the authored document model (Phase A of the program plan): the raw glTF JSON
itself is the authored state (never a second normalized model), mutated only through immutable,
inverse-tracked commands with structural sharing, so undo/redo, dirty-tracking, and byte-preserving
save all fall out of one representation.

Prefix: `DOC`.

## Requirements

### EditorDocument shape

- [DOC-001] (active) `EditorDocument.container` holds the pristine parse of the last successful save — it is not mutated by any in-memory command application.
- [DOC-002] (active) `EditorDocument.json` is the current authored glTF JSON as an immutable value — no command ever mutates a `json` object in place.
- [DOC-003] (active) `EditorDocument.rev` is a revision counter that changes by exactly one on every operation that changes `json` (a command push, an undo, or a redo), giving `StorageProvider.autosaveJournal`'s `sinceRev` parameter (SP-004) a well-defined value to journal against.
- [DOC-004] (active) `EditorDocument.dirtyRoots` is the set of canonical splice-root JSON pointers (see DOC-021) whose subtree has changed since the last successful save.

### applyCommand purity and structural sharing

- [DOC-005] (active) `applyCommand(document, command)` is a pure function: called twice with the same `document` and `command`, it produces equal output and never mutates its `document` argument or that argument's `json`.
- [DOC-006] (active) In `applyCommand`'s output `json`, every subtree not addressed by one of `command.patches` retains the exact object identity (`===`) it had in the input `json` (structural sharing).

### Command shape

- [DOC-007] (active) A `Command` carries `patches: JsonPatchOp[]` — the forward RFC-6902 operations, precomputed against the document state at the command's creation time.
- [DOC-008] (active) A `Command` carries `inverse: JsonPatchOp[]` — precomputed at creation time such that applying `inverse` to the result of applying `patches` restores a `json` deep-equal to the pre-`patches` state.
- [DOC-009] (active) A `Command` carries a `label: string` — a human-readable description shown in history UI.
- [DOC-010] (active) A `Command` carries an optional `coalesceKey`; `HistoryStack.push` merges a newly pushed command into the current top-of-history entry when both share the same defined `coalesceKey` (DOC-015).

### HistoryStack semantics

- [DOC-011] (active) `HistoryStack.push(command)` applies `command.patches` to the current document and appends `command` to the undo log.
- [DOC-012] (active) `HistoryStack.push(command)` clears the redo log.
- [DOC-013] (active) `HistoryStack.undo()` applies the most recently pushed (or redone) command's `inverse` patches to the current document and moves that command from the undo log to the redo log.
- [DOC-014] (active) `HistoryStack.redo()` re-applies the most recently undone command's `patches` to the current document and moves that command from the redo log back to the undo log.
- [DOC-015] (active) `HistoryStack.push` coalesces two consecutive commands that share the same defined `coalesceKey` into a single history entry (one undo/redo step) rather than stacking them as two.
- [DOC-016] (active) `HistoryStack.transact(fn)` groups every command pushed during the synchronous execution of `fn` into a single undo/redo step.
- [DOC-017] (active) The undo/redo log is linear (no branching): once any command has been undone, pushing a new command discards the entire existing redo log.
- [DOC-018] (active) `undo`/`redo` restore prior document states exclusively by applying `inverse`/`patches` JSON-Patch operations — `HistoryStack` never restores state by rewinding to a stored document snapshot pointer.
- [DOC-035] (active) Resolves the open question of whether a coalesced sequence of commands (DOC-015) bumps `rev` (DOC-003) once per pushed command or once per coalesced group, in favor of the former: every call to `applyCommand` that succeeds — including each individual `HistoryStack.push` later merged by coalescing (DOC-015) or grouped by `transact` (DOC-016) — bumps `rev` by exactly one. Coalescing/transacting change only how many entries `HistoryStack`'s undo/redo logs contain, never how many times `rev` advances; a single `undo()`/`redo()` call over a coalesced-or-transacted entry (however many underlying commands it groups) is itself one operation and so bumps `rev` by exactly one, per DOC-003.
- [DOC-036] (active) Resolves the open question of `HistoryStack`'s maximum depth: undo/redo depth is unbounded in v1 — no maximum depth or eviction policy is enforced. A memory-eviction policy (e.g. capping undo depth) is deferred to a future milestone.

### Index-stability policy

- [DOC-019] (active) A command that structurally deletes an array element such that subsequent elements' indices shift emits, within the same patch set, reference-fixup patches that rewrite every reference elsewhere in the document to a shifted index.
- [DOC-020] (active) Reference-fixup patches (DOC-019) cover `KHR_interactivity` pointer strings — index references embedded as extension string values, not only RFC-6902 `path`/`from` fields — wherever such a string encodes a shifted index.
- [DOC-021] (active) All index-shift reference fixups are produced by one shared `fixupReferences` helper, used by every command capable of shifting indices, rather than each command re-implementing its own fixup logic.

### Dirty-root computation

- [DOC-022] (active) Every patch path is truncated to its canonical splice root via a fixed path→canonical-splice-root table (e.g. a patch under `/nodes/3/...` truncates to `/nodes/3`; a patch under `/extensions/KHR_interactivity/graphs/2/...` truncates to `/extensions/KHR_interactivity/graphs/2`).
- [DOC-023] (active) `applyCommand` adds the canonical splice root (DOC-022) of every patch it applies to the resulting document's `dirtyRoots` set.
- [DOC-039] (active) `HistoryStack.entries()` returns every undo-log and redo-log entry (one per coalesced/transacted push) in chronological push order regardless of how many have since been undone, each exposing a representative `label` (its first command's `Command.label`) and its zero-based `index` in that order; `HistoryStack.currentIndex()` returns the index of the most recently applied entry within that same order, or `-1` if none has been applied yet.
- [DOC-040] (active) `HistoryStack.onApply(handler)` registers a callback invoked, after `push`, `undo`, or `redo` mutates `document`, with exactly the forward-direction `JsonPatchOp[]` just applied to reach the new `document.json` (the command's `patches` for `push`/`redo`, its `inverse` for `undo`), so a caller (e.g. a `RenderHost` sync layer) can apply the same delta without recomputing a diff; returns an unsubscribe function.
- [DOC-038] (active) Resolves DOC-022's "full table" open question. The path→canonical-splice-root table is, in priority order: (1) `/extensions/KHR_interactivity/graphs/{N}/...` truncates to `/extensions/KHR_interactivity/graphs/{N}` — one interactivity graph is the editable unit, so any add/remove/reference-fixup entirely inside one graph (new nodes, declarations, variables, custom events, or index-shifted references) stays inside that graph's own root and never needs the reserialize fallback (DOC-025) merely for being "inside an existing graph"; (2) `/extensions/{name}/...` for any other extension (including `KHR_audio_emitter`, per the plan's own example) truncates to `/extensions/{name}` — the whole extension object is the root, so most future extensions need no table change at all, only ones wanting rule-1-style per-element granularity do; (3) `/{arrayRootKey}/{N}/...` for every top-level glTF array root (`nodes`, `meshes`, `materials`, `textures`, `images`, `samplers`, `skins`, `accessors`, `bufferViews`, `buffers`, `animations`, `scenes`, `cameras`) truncates to `/{arrayRootKey}/{N}` — one array element is the editable unit (this is also where `node.extras.gltfi.{x,y}`, DOC-027, ends up, since it is nested under a node root); (4) anything else (`/scene`, `/asset`, `/extensionsUsed`, `/extensionsRequired`, `/extras`, or any future unrecognized top-level key) truncates to that top-level key itself, since these are not arrays of independently-editable elements.

### Save semantics

- [DOC-024] (active) Save splices each entry in `dirtyRoots` into the pristine container's bytes independently, via `locateJsonSpan`/`applyEdits`, one root at a time.
- [DOC-025] (active) When a dirty root is newly created, or its position has been renumbered since the last save such that `locateJsonSpan` cannot locate a stable byte span for it, save falls back to reserializing the entire document for that save — the same fallback `spliceGraph` already uses.
- [DOC-026] (active) Save's byte output is identical to the pristine container's bytes at every byte span outside the dirty roots it spliced (byte-preservation outside dirty roots is asserted by the fallback path's own tests, not merely assumed).

### Node-position storage

- [DOC-027] (active) Editor-authored 2D positions for interactivity-graph canvas nodes are stored at `node.extras.gltfi.{x,y}` inside the authored glTF JSON, so positions travel with the exported file and are undoable through the normal command/patch mechanism.

### State homes

- [DOC-028] (active) Graph node positions (`node.extras.gltfi.{x,y}`, DOC-027) live in the authored asset (`EditorDocument.json`): they are saved with the `.glb`/`.gltf` and are undoable via `HistoryStack`.
- [DOC-029] (active) Panel layout and camera bookmarks live in a per-project sidecar persisted via `StorageProvider` (`ProjectData.sidecar`, SP-012) — not in the glTF JSON, and not undoable via `HistoryStack`.
- [DOC-030] (active) Selection, hover, and play-mode state live only in the ephemeral in-memory store — never written into `EditorDocument.json` or the sidecar.

### Document frozen during play

- [DOC-031] (active) `EditorDocument` is frozen for the duration of play mode: no `Command` may be applied to it (via `applyCommand` or `HistoryStack`) while `PlayController` is running. Play-mode state changes go exclusively through `PlayController`'s fan-out (`SceneAdapter.applyPointer`), never through `applyCommand`/`HistoryStack`.
- [DOC-037] (active) Resolves the open question of whether `applyCommand`/`HistoryStack` throw, no-op, or queue when a command is attempted while `EditorDocument` is frozen (DOC-031), in favor of throwing: `applyCommand` throws a typed `DocumentFrozenError` (not a no-op, not a queued/deferred application) when called against a frozen document; `HistoryStack.push`/`undo`/`redo` propagate the same error rather than swallowing it. UI command dispatch is expected to prevent commands from reaching `applyCommand` while play is running, upstream of this throw.
- [DOC-045] (active) `HistoryStack` exposes `freeze()`/`unfreeze()` methods that call `freezeDocument`/`unfreezeDocument` (`DOC-031`) on its currently-held `EditorDocument` and replace it in place, so an existing live `HistoryStack` instance (not just one freshly constructed around an already-frozen document) can be frozen for the duration of play mode and unfrozen on stop.

### Property-test obligations

- [DOC-032] (active) For every command type, applying `command.patches` to a document and then applying that same command's `inverse` yields a `json` deep-equal to the document's `json` before `patches` was applied (command+inverse round-trip property).
- [DOC-033] (active) For any sequence of commands pushed onto a `HistoryStack` starting from a given document, calling `undo()` once per pushed command yields a `json` deep-equal to that document's `json` before the first command was pushed (undo-all ≡ initial property).
- [DOC-034] (active) For any sequence of commands followed by save, reparsing the saved bytes yields a `json` deep-equal to the in-memory `json`, and every byte span outside the dirty roots touched by that sequence is byte-identical to the pristine container's corresponding span (save invariant).

### GraphEdit scaffolding helpers

- [DOC-041] (active) `GraphEdit.ensureGraph(document, graphIndex)` finds-or-scaffolds `extensions.KHR_interactivity.graphs[graphIndex]` (empty `types`/`declarations`/`variables`/`events`/`nodes` arrays, plus the extension's `graph` pointer and an `extensionsUsed` entry when either is missing) as a single command, returning a no-op command (empty `patches`/`inverse`) when that graph already exists — every other `GraphEdit` factory assumes its target graph already exists; this is the one factory a caller (e.g. `specs/ux-inspector.md`'s `UX-412` pointer-shortcut "Add pointer/…" actions) uses first when it can't assume that.
- [DOC-042] (active) `GraphEdit.ensureType(document, graphIndex, signature)` finds-or-appends a `{ signature }` entry into `graph.types`, mirroring `ensureDeclaration`'s (DOC-021) find-or-append semantics for `graph.declarations`, so a caller that must populate a node's `configuration.type` (a `graph.types` index) gets a stable index without duplicating an already-declared signature.
- [DOC-043] (active) `GraphEdit.replaceGraph(document, graphIndex, newGraph)` replaces `extensions.KHR_interactivity.graphs[graphIndex]` wholesale with `newGraph` as a single command whose forward patch is one `replace` at the graph root and whose inverse restores the prior graph value exactly (DOC-007/DOC-008) — it does not diff node-by-node. `specs/ux-script.md`'s `UX-711` "Apply → Graph" action is this factory's one caller: it swaps in a freshly parsed-and-exported script as one undo/redo step.
- [DOC-044] (active) `GraphEdit.setNodeConfig(document, graphIndex, nodeIndex, field, value)` sets `nodes[nodeIndex].configuration[field]` to `{ value }` (add-or-replace), mirroring `setLiteral`'s shape for `values` — the generic single-field config primitive M4's config-field editor (`specs/ux-graph-canvas.md`'s config-editing note) and the pointer-picker dialog's retarget flow (`specs/ux-pointer-picker.md`'s `UX-906`) build their specific edits on top of, alongside `ensureType` (DOC-042) when a field's value needs a fresh `types[]` index. `GraphEdit.addPointerNode`'s `kind` parameter additionally accepts `"get"` (alongside `"set"`/`"interpolate"`) as of the same change, for `specs/ux-graph-canvas.md`'s `UX-508` drag-drop drop-menu's `pointer/get` option.

### Minimal append-only structural SceneEdit factories

- [DOC-046] (active) `SceneEdit` provides a minimal, APPEND-ONLY subset of structural scene-editing factories — `addNode`, `addMesh`, `addMaterial`, `addAccessor`, `addBufferView`, `addBuffer` — each appending exactly one element to `json.{nodes,meshes,materials,accessors,bufferViews,buffers}` respectively via a single `add` `JsonPatchOp`, and returning `{command, index}` (mirroring `GraphEdit.ensureDeclaration`'s shape, DOC-021) so a caller can chain further edits against the new element's stable index without re-reading the document. `SceneEdit.addNode` additionally appends the new node's index into the current default scene's `nodes` array (`json.scenes[json.scene ?? 0].nodes`) as part of the SAME command (via `combineCommandParts`) when its `addToScene` option is true (the default), so a newly added node is scene-visible without a second undo step. These factories are scoped to APPENDS ONLY: no reparenting under an existing node, no removal, and no reference-fixup pass (DOC-019..021) — there is nothing to fix up when only appending to the end of an array. This lands ahead of M8 per `docs/adr/0004-agentic-authoring-as-command-producer.md`'s "asset generation pulls scene-structural mutation earlier than the M8 plan assumed" consequence: the v1 mock `AgentService`'s procedural "add a cube" asset-generation template (`specs/agent-service.md`'s AG-014) needs to add a new mesh+node to the scene, and this append-only subset is sufficient for that without pulling forward reparenting or deletion. `SceneEdit.removeNode` is real as of DOC-048 (M8 part 1); `reparentNode`/`duplicateNode` are real as of DOC-052/053 (M8 part 2) — scene authoring's add/delete/reparent/duplicate structural factories are all real as of that change.
- [DOC-047] (active) M8-lite extension of DOC-046, for the scene tree's "+ Add" menu (`specs/ux-scene-tree.md`'s `UX-206`/`UX-213`): `SceneEdit.addNode` (and every factory below) additionally accepts `opts.parentNodeIndex` — when given, the new node's index is appended to THAT node's `children` array (creating it if absent) instead of the current default scene's root `nodes` array, still as part of the SAME combined command; still append-only (no reparenting of anything that already exists). Four new composite factories each build a complete, ready-to-render subtree as ONE combined command: `addPrimitiveMeshNode(document, "cube"|"sphere"|"plane", name, opts)` (a generated buffer+3 bufferViews+3 accessors+material+mesh+node, via `primitives.ts`'s `cubeGeometry`/`sphereGeometry`/`planeGeometry` + `encodeCubeBuffer`); `addLightNode(document, name, opts)` (a `KHR_lights_punctual` light + a referencing node, scaffolding the extension's root `lights[]` registry and its `extensionsUsed` entry on first use — the same find-or-create pattern `GraphEdit.ensureGraph`, DOC-041, established for `KHR_interactivity`); `addCameraNode(document, name, opts)` (a core-glTF `cameras[]` entry + a referencing node); and `addAudioEmitterNode(document, name, opts)` (a generated silent-WAV buffer + bufferView + `KHR_audio_emitter` `audio`/`sources`/`emitters` entries + a referencing node, same extensionsUsed scaffolding as lights). All four return `{command, index}` where `index` is the new NODE's index, mirroring `addNode`'s own shape.

### Structural node deletion (M8 part 1)

- [DOC-048] (active) `SceneEdit.removeNode(document, nodeIndex)` deletes `nodeIndex` AND its entire descendant subtree (every node transitively reachable via `children`) as ONE combined, undoable command — the resolved choice for DOC-046/047's "deletion... deferred to M8" note, in favor of whole-subtree deletion over a "delete keeping children" variant (the latter would need to decide where orphaned children re-attach; deferred, and expected to be its own future factory rather than a `removeNode` option). Returns `{command, parentIndex}`: `parentIndex` is the index the node's immediate PARENT will have AFTER the command applies (accounting for any shift caused by deleting subtree members with a smaller original index than the parent), or `null` when `nodeIndex` was a scene-root node — `specs/ux-scene-tree.md`'s `UX-214` "selection moves to the parent" policy consumes this directly rather than re-deriving it. Implemented by removing the subtree's member nodes one at a time in DESCENDING original-index order (the largest remaining index first) — an ordering that needs no cross-step index-translation bookkeeping, since removing the current maximum never shifts any other still-pending (necessarily smaller) target — with each individual step's fixup-then-remove pair following the same ordering `GraphEdit.removeNode` already established (DOC-019), and every step's `{patches, inverse}` folded together via `combineCommandParts` into the one command that `HistoryStack.push` sees as a single undo/redo entry.
- [DOC-049] (active) `SceneEdit.removeNode`'s reference-fixup pass (DOC-019..021's shared `fixupReferences` helper, extended by three new `ReferenceKind`s this adds — `indexArray`, `indexScalar`, `graphConfigLiteral`, `fixup-references.ts`) covers, for each subtree member being removed: `scenes[].nodes` and every OTHER node's `children` array (raw-number arrays — an entry EQUAL to the removed index is DROPPED from the array, not left dangling; an entry greater than it shifts down by one); `skins[].joints`/`skins[].skeleton` (same drop-or-shift policy, purely defensive — `packages/editor-core` never authors or renders skins, but must not corrupt an IMPORTED asset's skin data); `animations[].channels` (a channel whose `target.node` equals the removed index is DROPPED from the array — the resolved choice over retargeting to nothing — its sibling channels' `target.node` shifts down by one when above the removed index, untouched below it); and, inside every `KHR_interactivity` graph, the literal `configuration.nodeIndex` field `event/onSelect`/`onHoverIn`/`onHoverOut` handler nodes carry (`packages/usage-index`'s `literalNumber` reads the identical field) — shifted when above the removed index, left DANGLING (not repaired) when equal to it or when it is the `-1` "any node" sentinel, mirroring DOC-020's existing dangling-pointer-literal policy rather than DOC-048's own array drop-on-match policy, since a graph-authored reference (unlike a core structural array element) is a validity concern `@gltfi/ir`'s `validateGraph`/the usage-index UI can surface, not one `removeNode` itself must repair. `KHR_interactivity` pointer-template literal strings (`pointer/get|set|interpolate`'s `configuration.pointer`, e.g. `"/nodes/3/translation"`) get the SAME dangling-on-match/shift-above treatment via the pre-existing `jsonPointerLiteral` kind (DOC-020), scanned across the whole document, not scoped per-graph. Deliberately NOT touched: a graph node's OWN `{node, socket}` value/flow wiring (`graphNodeRef`, DOC-019) — that addresses ANOTHER GRAPH NODE, a wholly separate index space from the scene node `removeNode` deletes, and remains `GraphEdit.removeNode`'s own concern exclusively.
- [DOC-050] (active) `SceneEdit.removeNode` never garbage-collects a resource merely because deleting a node left it unreferenced: `meshes`, `materials`, `accessors`, `bufferViews`, `buffers`, `cameras`, `extensions.KHR_lights_punctual.lights[]`, and `extensions.KHR_audio_emitter.{audio,sources,emitters}[]` all stay exactly as they were (an orphaned entry simply has nothing pointing at it afterward) — extending DOC-046's original "these factories don't garbage-collect" byte-preserving philosophy to deletion. A node's OWN outgoing references (`node.camera`, `node.mesh`, `node.extensions.KHR_lights_punctual.light`, `node.extensions.KHR_audio_emitter.emitter`) need no fixup at all when that node is deleted — they simply vanish with the node object itself, since none of them index the `nodes` array being shifted. This is a deliberate v1 choice, not an oversight: these registries can be shared by multiple nodes (a mesh referenced by two nodes must not vanish because one of them is deleted), so safe garbage collection would need real reachability analysis across the whole document — out of scope here, matching the same reasoning DOC-046 already gave for its append-only factories.
- [DOC-051] (active) Resolves a `trySplice` (`save.ts`, DOC-024/DOC-025) gap DOC-048's property tests (DOC-032/033/034's `property.test.ts`) surfaced: `dirtyRoots` (DOC-004) records only the canonical splice root of each patch's OWN path, so a structural `remove` at a top-level array element (e.g. `/nodes/{i}`) — which, per RFC 6902 array semantics, implicitly shifts every LATER element of that SAME array down by one position — marks no dirty root for the elements it silently moved. Splicing only the explicitly-dirty root(s) in that case can succeed at locating a (stale) byte span for each one and still produce WRONG bytes: `SceneEdit.removeNode` is the first command that ever shrinks a top-level array (every prior structural factory, DOC-046/047, was append-only, which never shifts an EXISTING element), so this was previously unreachable. Fixed generally rather than by enumerating every shift-shaped command: `trySplice` now reparses its own spliced result and deep-equality-checks it against the true in-memory `document.json` before returning it as a success; any mismatch falls through to the existing whole-document `reserialize` fallback (DOC-025) instead of ever returning bytes that would violate DOC-034's own "reparsing saved bytes deep-equals the in-memory json" invariant.

### Structural node reparenting and duplication (M8 part 2 — completes scene authoring)

- [DOC-052] (active) `SceneEdit.reparentNode(document, nodeIndex, newParentIndex, insertIndex?, opts?)` moves `nodeIndex` (and, implicitly, its entire subtree — `children` arrays are the only parent link, so the whole subtree necessarily moves with its root, no work of its own required) from its current parent's `children` array (or the current default scene's root `nodes` array, when it has none) to `newParentIndex`'s `children` array, or the scene root when `newParentIndex` is `null`, as ONE undoable command. This is a plain two-array MEMBERSHIP move — remove `nodeIndex` from whichever array currently lists it, insert it into the new one (at `insertIndex` when given, else appended as the last child/root, mirroring `addNode`'s own default landing spot for a brand-new node, DOC-047) — never a `nodes`-array structural remove/re-add. Resolves this file's own former M8-stub note (DOC-046/048): reparenting an EXISTING node is real as of this change. Rejects with a typed `CycleReparentError` (`packages/editor-core/src/scene-edit.ts`) — no partial application — when `newParentIndex` is `nodeIndex` itself or one of its own descendants (walked via the same DFS `collectSubtreeIndices` helper DOC-048's `removeNode` uses), which would otherwise disconnect the moved subtree or create an unwalkable cycle; reparenting a node back under its OWN current parent is explicitly allowed, not treated as a no-op error — with no `insertIndex` it simply moves the node to be the LAST child among its current siblings. **World-transform policy (resolved, not left open): WORLD transform is preserved by DEFAULT.** A reparent is a purely structural "move this under that other node" gesture, not an implicit relocation, so `reparentNode` computes `nodeIndex`'s current world matrix (walking its OLD parent chain, `mat-utils.ts`), and `newParentIndex`'s own world matrix (identity for a root landing), then solves `newLocal = inverse(newParentWorld) * oldWorld` — the unique local transform reproducing the exact same world matrix under the new parent — and writes it back in whichever shape the node already used (`matrix` array, or explicit `translation`/`rotation`/`scale`, all three, since a rotated/scaled new ancestor chain can turn a previously-identity component non-identity). Both world matrices are computed against the PRE-move document, which the cycle check above guarantees is always safe: `newParentIndex` can never be one of `nodeIndex`'s own descendants, so `nodeIndex` can never be one of `newParentIndex`'s ancestors, so detaching `nodeIndex` first can never change `newParentIndex`'s own world matrix. `opts.keepLocal: true` opts OUT, restoring the simpler "local transform carries over unchanged, world transform generally changes" behavior for a caller that wants it (none currently does — the scene tree's drag-and-drop, `specs/ux-scene-tree.md`'s `UX-215`, always wants the default).
- [DOC-053] (active) `SceneEdit.duplicateNode(document, nodeIndex)` deep-copies `nodeIndex` and its entire descendant subtree as brand-new, APPENDED `nodes` entries (append-only, like `addNode`/`addPrimitiveMeshNode`/etc, DOC-046/047 — never reparenting or deleting anything that already exists) as ONE undoable command, returning `{command, index}` (mirroring every other structural add factory's shape) where `index` is the new copy of `nodeIndex` itself. Each duplicated node object shares every non-node resource reference completely unchanged (`mesh`/`camera`/`extensions.KHR_lights_punctual.light`/`extensions.KHR_audio_emitter.emitter`/`translation`/`rotation`/`scale`/`matrix`/`weights`/etc — none of these are copied or reallocated; two `nodes` entries referencing the same `mesh` index is exactly how glTF instancing already works, not something needing special-case handling) — only `name` (each duplicated node's own name gets a `" copy"` suffix, defaulting to `Node {originalIndex}` first when unnamed, applied to EVERY node in the copied subtree, not just its root) and `children` (remapped to the new indices of the duplicated descendants, preserving the copied subtree's internal shape; omitted, not `[]`, on a duplicated leaf — DOC-048/049/052's established convention) are rewritten. The new subtree root is spliced in as a SIBLING immediately after the original, into the exact same membership array the original belongs to (parent's `children` or the scene root), reusing `reparentNode`'s own insert-at-position mechanism. Deliberately NOT auto-wired into any interactivity graph: a duplicated node's new index is never added to any existing `event/onSelect`/`onHoverIn`/`onHoverOut` handler's `configuration.nodeIndex`, and no new graph nodes are created on the copy's behalf — a duplicate of a node some handler addresses does not inherit that handler's behavior; the user re-wires the copy explicitly (`specs/ux-graph-canvas.md`'s `UX-509` drag-drop, or Copilot). This is a resolved policy choice, not an oversight: auto-wiring would require understanding and cloning arbitrary graph-node subgraphs reachable from a handler, a different and open-ended feature from "copy this node's own scene data".
- [DOC-054] (active) Neither `reparentNode` nor `duplicateNode` needs ANY `fixupReferences` (DOC-019..021) pass, and this is the key structural difference from `removeNode` (DOC-048/049): `reparentNode` never deletes a `nodes` array element or changes any node's INDEX (it only moves which membership array currently lists an unchanged index), and `duplicateNode` only ever APPENDS new elements (like every DOC-046/047 factory) — appending never shifts an existing element's index either. Every existing reference to the moved/duplicated-FROM node elsewhere in the document — another node's `children` entry, a `scenes[].nodes` entry, an `event/onSelect`/`onHoverIn`/`onHoverOut` handler's literal `configuration.nodeIndex`, a `pointer/get|set|interpolate` node's literal `configuration.pointer` string, an animation channel's `target.node`, a `skins[].joints`/`skeleton` entry — addresses that node by its unchanged numeric index and needs zero changes of its own; this is verified directly by both `packages/editor-core/src/scene-edit.test.ts`'s and `property.test.ts`'s DOC-052/053 test suites, which assert a pre-existing `event/onSelect` literal's `configuration.nodeIndex` reads identically before and after every reparent/duplicate operation exercised. Completes scene authoring's structural quartet (add/delete/reparent/duplicate, DOC-046..048/052/053) as of this change; sibling reordering beyond `reparentNode`'s own `insertIndex` parameter (e.g. a dedicated "move sibling up/down" UI affordance) remains a possible future polish, not a v1 gap — `insertIndex` already makes same-parent sibling reordering mechanically possible for any caller that wants to build on it.

### Variable/custom-event management (graph)

- [DOC-055] (active) Task ("in the node graph there is no way to edit variables"): `GraphEdit` gains five new factories — `renameVariable(document, graphIndex, variableIndex, id)` (sets `variables[i].id`; every `variable/get|set|interpolate` reference is BY INDEX, never by id, so a rename never touches a single referencing node), `setVariableType(document, graphIndex, variableIndex, signature)` (retypes `variables[i].type` to a find-or-appended, `ensureType`/DOC-042, `types[]` index, resizing `variables[i].value` to the new signature's component count in the SAME combined command — see `resizeVariableValue`/`coerceComponent`'s own doc comments for the exact truncate/pad-and-coerce rule), `setVariableDefault(document, graphIndex, variableIndex, value)` (sets `variables[i].value` outright, no resize), and `removeVariable`/`renameCustomEvent`/`removeCustomEvent` (the last two mirroring `renameVariable`/`removeVariable` for `graph.events`, minus type/default — an event has neither). **Resolved delete-vs-dangle policy** (evaluated against DOC-020's existing dangling-literal precedent and DOC-048/049's drop-or-shift precedent for core structural arrays): `removeVariable`/`removeCustomEvent` are **BLOCKED** (throw `VariableInUseError`/`CustomEventInUseError`, carrying `variableIndex`/`eventIndex` and an exact `usageCount` of distinct referencing nodes) when any `variable/get|set|interpolate` or `event/send|receive` node still references the target index — the opposite of DOC-020/DOC-049's "leave dangling, let the validator flag it" policy for scene-node/pointer references, because a `variables[]`/`events[]` index is a DECLARATION TABLE every consumer (the KHR_interactivity runtime, `@gltfi/verify`'s structural validator, this package's own `map-graph.ts`) assumes is fully populated for every index any node cites — a dangling variable/event index is a harder failure mode than a dangling scene-node reference (which several consumers already tolerate as "inert"/"any node"), so blocking with an actionable, exact usage count was chosen over authoring a further "missing variable" dangling-reference class. When unused, the element is removed AND every surviving reference above it is shifted down by one in the SAME combined command (`shiftVariableRefsInNodes`/`shiftEventRefsInNodes`) — `variables[]`/`events[]` had no pre-existing shared fixup path (`fixup-references.ts`'s kinds are all scene/graph-node-index-shaped, not this table), so these factories own their own, narrowly scoped shift logic rather than extending that shared helper. **Resolved retype policy**: `setVariableType` does **NOT** check usage and never blocks — retyping an in-use variable is ALLOWED unconditionally; any `variable/get|set|interpolate` node whose own edges assumed the prior type becomes a real finding through the EXISTING `@gltfi/verify`/`@gltfi/ir` validation pipeline (`packages/graph-canvas`'s `validateInteractivityGraph`, already wired to graph changes) the next time it runs — no new validation logic was added for this, deliberately: the retype-then-validate flow reuses infrastructure that already re-runs on every graph edit rather than duplicating a type-mismatch check `@gltfi/verify` already owns. `countVariableUsage`/`countEventUsage` (the exact functions `removeVariable`/`removeCustomEvent` use internally to decide block-vs-allow) are exported, so a caller (`packages/graph-canvas`'s Variables panel) can display the identical count its delete button's enabled/disabled state is gated on — the two can never drift apart because they're the same function call.
### AudioGraphEdit command factories (M7 audio-graph editing)

- [DOC-056] (active) `AudioGraphEdit.ensureGraph(document, graphIndex)` finds-or-scaffolds `extensions.KHR_audio_graph.graphs[graphIndex]` (empty `nodes`/`connections` arrays, plus an `extensionsUsed` entry when missing) as a single command, mirroring `GraphEdit.ensureGraph`'s (DOC-041) find-or-create semantics one extension over — a no-op command when that graph already exists. Every other `AudioGraphEdit` factory assumes its target graph already exists. `AudioGraphEdit`'s command-side endpoint types, `AudioEndpointSource` (`{kind:"node",index,output?}` | `{kind:"source",sourceIndex}`) and `AudioEndpointTarget` (`{kind:"node",index,input?}` | `{kind:"emitter",emitterIndex}`), name the same three entities `@gltf-studio/audio-canvas`'s `map-audio-graph.ts` projection already renders as canvas nodes (a real `graph.nodes[]` entry, a synthetic `audio-buffer-source` node per bound `KHR_audio_emitter` source, and a synthetic terminal `emitter` node per bound emitter, UX-607) — resolving them back to a `graph.nodes[]`/source/emitter identity from a canvas selection is `audio-canvas`'s own `audio-entity.ts` concern, out of `editor-core`'s scope.
- [DOC-057] (active) `AudioGraphEdit.addNode(document, graphIndex, kind, params, opts)` appends a `{ kind, params }` entry (plus optional `label`/position `extras`, DOC-058) to `graph.nodes[]`; `removeNode(document, graphIndex, nodeIndex)` removes it and rewrites `connections[]`/`inputs[]`/`outputs[]` (whichever exist) to drop every entry that referenced it and shift every surviving node-index reference above it down by one; `setNodeParam(document, graphIndex, nodeIndex, key, value)` sets `graph.nodes[nodeIndex].params[key]` (add-or-replace, coalesced per `graphIndex:nodeIndex:key` so a dragged slider commits as one undo step), mirroring `setNodeConfig`'s (DOC-044) shape one level down into a node's `params` bag instead of its `configuration`. Node `kind`/`params` shapes come from the ratified `KHR_audio_graph.node.schema.json`'s per-kind `oneOf` list, cataloged (with defaults/ranges/enum options) in `@gltf-studio/audio-canvas`'s `audio-node-registry.ts` — the palette's only source of truth for what `addNode`'s `kind` argument may be. `removeNode`'s fixup does NOT reuse `fixup-references.ts`'s `ReferenceKind` machinery (none of its five kinds fit an array of `{from,to}` connection objects, only object-keyed value/flow maps or raw index arrays/scalars) — see DOC-059 for the array-rewrite strategy it uses instead, shared with `connectAudio`/`disconnectAudio`.
- [DOC-058] (active) `AudioGraphEdit.setNodePosition(document, graphIndex, nodeIndex, x, y)` stores a REAL audio-graph node's canvas position at `graph.nodes[nodeIndex].extras.gltfi.{x,y}` — resolving `specs/ux-audio-graph.md`'s `OPEN(UX-audiograph-position-tbd)` by reusing DOC-027's exact `extras.gltfi` convention one level down (`KHR_audio_graph.node.schema.json` allows `extras` on every node the same way glTF's own `nodes[]` does). No code change was needed in `@gltf-studio/graph-canvas` for this to render: `graph-view.tsx`'s `nodePosition()` already reads `node.raw.extras?.gltfi` generically off whatever object `MappedNode.raw` is, and `map-audio-graph.ts` already sets a real node's `raw` to its literal `KHRGraphNodeSpec` (unchanged by M7). Not applicable to the synthetic `audio-buffer-source`/terminal-`emitter` nodes (DOC-056) — they are not `graph.nodes[]` entries and have no home for `extras` in this graph; `audio-canvas`'s wiring layer does not call this factory for them, and their canvas position is never persisted (falls back to the ELK auto-layout on every reload) — a known, accepted v1 scoping limit, not a bug.
- [DOC-059] (active) `AudioGraphEdit.connectAudio(document, graphIndex, from, to)`/`disconnectAudio(document, graphIndex, to)` wire/unwire one of `connections[]` (node→node), `inputs[]` (`KHR_audio_emitter` source→node), or `outputs[]` (node→emitter), selected by `from`/`to`'s `AudioEndpointSource`/`AudioEndpointTarget` kind (DOC-056) — `source→emitter` (bypassing every processing node) is rejected (thrown), since neither array can express a direct source/emitter binding. `connectAudio` overwrites any existing entry already wired into the SAME `to` identity ("last write wins", the same effective semantics `GraphEdit.connectValue`'s per-socket map has). Unlike `GraphEdit`'s per-key `setPathFragment`/element-level `fixupReferences` approach (designed for object-keyed maps and per-element index-shift patches respectively), every `AudioGraphEdit` factory that touches `connections[]`/`inputs[]`/`outputs[]` (including `removeNode`'s fixup, DOC-057) computes the WHOLE next array value from the current one and emits a single `replace` patch (+ exact-prior-value inverse) — simpler and still fully DOC-008-exact for these arrays' realistic sizes, and it sidesteps DOC-019-style patch-ordering hazards entirely since every fragment in one command is computed against the same pre-edit `document.json` and touches a disjoint path. `canonicalSpliceRoot` (`splice-root.ts`, DOC-038) gained a matching per-graph splice root for `extensions.KHR_audio_graph.graphs.{N}` (rule 1b, alongside `KHR_interactivity`'s existing rule 1) so these commands dirty only their own graph, not the whole extension (DOC-038's rule-2 default) — exactly the table extension this spec's own "Open questions" section already told future PRs to make.

### Richer inspector: Light/Camera/texture-slot SceneEdit factories

- [DOC-060] (active) Richer inspector (`specs/ux-inspector.md`'s `UX-415`..`418`): `SceneEdit` gains four new property-editing factories, mirroring `setMaterialProperty`/`setAudioEmitterProperty`'s existing by-index-into-a-registry shape rather than inventing a new one. `setLightProperty(document, lightIndex, propertyPath, value)` sets an arbitrary property on the ROOT `extensions.KHR_lights_punctual.lights[lightIndex]` registry entry (addressed by LIGHT index, like `setAudioEmitterProperty`'s emitter-index addressing — NOT by the node that happens to reference it). `setCameraProperty(document, cameraIndex, propertyPath, value)` sets an arbitrary property on core-glTF's `cameras[cameraIndex]` (no extension involved, unlike lights/audio emitters). `clearMaterialTexture(document, materialIndex, textureInfoPath)` removes a whole texture-info object (e.g. `["pbrMetallicRoughness", "baseColorTexture"]`) via `deletePathFragment` — the Inspector's Texture Slots "Clear" control; texture-info REPLACEMENT (assigning a new image) has no factory yet, a real follow-up. `setMaterialTextureTransform(document, materialIndex, textureInfoPath, field, value)` sets ONE `KHR_texture_transform` field (`offset`/`scale`/`rotation`) on a texture-info object, scaffolding the extension's `extensionsUsed` entry in the SAME combined command when absent (mirroring `addLightNode`/`addAudioEmitterNode`'s own `ensureExtensionUsedFragment` find-or-scaffold pattern, DOC-047) — the scaffold step is unconditional and idempotent rather than gated on "is this the first write", the same simplicity tradeoff `addLightNode` already made for its own `extensionsUsed` entry. None of the four need a `canonicalSpliceRoot` (DOC-038) table change: `cameras`/`materials` writes already truncate via rule 3 (existing array-root entries), and `extensions.KHR_lights_punctual.lights[N]` writes fall through to rule 2's existing whole-extension-object default (dirtying the whole `KHR_lights_punctual` extension rather than just the one light — coarser, but correct, and consistent with `KHR_audio_emitter`'s own same-default granularity).

### Journal-consistent undo/redo (task #36)

- [DOC-061] (active) `HistoryStack.undo()`/`redo()` (DOC-013/DOC-014) now RETURN the exact forward-direction `JsonPatchOp[]` they just applied — the identical value DOC-040's `onApply` handlers already receive for the same call (`undo()`'s inverse patches, `redo()`'s forward patches; a coalesced/transacted entry, DOC-015/DOC-016, returns every underlying command's patches flattened in the same order `entryToCommand` already establishes for `onApply`), instead of `void`. Closes a gap `specs/ux-shell.md`'s `UX-123`/`UX-125` (SP-004 autosave journal) had documented but not fixed: `packages/app`'s store called `history.push(command)` and journaled `command.patches` on every edit, but had no equivalent value to journal for `history.undo()`/`redo()`, which mutate `document` exactly the same way — this return value is what closes that gap, consumed by `undo()`/`redo()`'s own store actions (see `specs/ux-shell.md`'s matching follow-up note for the consuming half of this fix). `HistoryStack` itself gains no journal/storage dependency — `packages/editor-core` has never imported `@gltf-studio/engine-api`'s `StorageProvider` and still doesn't — this is purely a richer return value a caller MAY use, not a new obligation `HistoryStack` enforces on any caller that doesn't.

### Emitter/environment/listener authoring SceneEdit factories (audio pass 3/3)

- [DOC-062] (active) Emitter/environment authoring (`specs/ux-inspector.md`'s `UX-419`..`422`): `SceneEdit` gains nine new factories, all mirroring `setAudioEmitterProperty`/`setLightProperty`'s existing by-index-into-a-root-registry shape. `setAudioSourceProperty(document, sourceIndex, propertyPath, value)` sets an arbitrary property on `extensions.KHR_audio_emitter.sources[sourceIndex]` (gain/playbackRate/loop/autoplay/audio) — a SEPARATE factory from `setAudioEmitterProperty` because `sources[]` and `emitters[]` are two distinct root arrays an emitter only references by index. `addAudioEnvironment(document, name, opts)`/`setAudioEnvironmentProperty(document, environmentIndex, propertyPath, value)` create and edit ROOT `extensions.KHR_audio_environment.environments[]` entries (reverb preset/mix, doppler), scaffolding `extensionsUsed`; `addAudioListener`/`setAudioListenerProperty` do the same for `extensions.KHR_audio_environment.listeners[]` (gain, spatializationModel). `setNodeAudioEnvironmentProperty(document, nodeIndex, propertyPath, value)` sets an arbitrary field on a NODE's own `extensions.KHR_audio_environment` object — the one JSON location the real extension overloads for BOTH a reverb-zone binding (`environment`/`shape`/`blendDistance`/`priority`) and a listener binding (`listener`), per `WebAudioHost`'s own `GltfNodeAudio` type; `addAudioZone(document, nodeIndex, environmentIndex, opts)` scaffolds that object wholesale (default shape a radius-5 sphere) plus `extensionsUsed` in one command, matching `addLightNode`'s find-or-scaffold convention. `setSceneAudioEnvironment`/`setSceneAudioActiveListener(document, sceneIndex, indexOrNull)` set-or-clear (via `deletePathFragment` when given `null`) `scenes[sceneIndex].extensions.KHR_audio_environment.environment`/`activeListener` — the scene-wide zone-selection fallback and pinned-listener override `spatial.ts`'s `selectEnvironment`/`WebAudioHost.selectListener` both read. ## Open questions

All four open questions this spec previously carried were resolved in the M1 PR that scaffolded
`packages/editor-core` (see DOC-035, DOC-036, DOC-037, DOC-038 above for the resolutions
themselves): rev-bump semantics under coalescing (DOC-035), `HistoryStack` depth (DOC-036),
command-during-play-freeze behavior (DOC-037), and the full splice-root table (DOC-038). None
remain open as of M1.

rule-1-style per-element granularity for some extension other than `KHR_interactivity`) should
extend DOC-038's table directly rather than reopening this section.
